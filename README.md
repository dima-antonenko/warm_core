# warm_core

Пул потоков для Linux. Он держит работу на одном физическом ядре процессора, чтобы данные не приходилось каждый раз заново тащить из оперативной памяти.

Крейт читает топологию процессора из `/sys` и закрепляет каждый рабочий поток за одним логическим CPU через `sched_setaffinity`. Зависимость одна: `libc`.

Ниже всё разложено с нуля: что такое ядро, поток и кэш, почему переключение между потоками дорогое, что именно делает этот пул и какой от этого прирост на замеренной задаче.

## Коротко, если не хочется читать всё

На машине, где это замеряли (Intel i7-8750H), одна и та же работа заняла:

| Вариант | Время |
|---|---|
| Обычные потоки `std::thread`, между проходами `yield_now` | 37 мс |
| `warm_core` | 31 мс |

`warm_core` закончил ту же работу примерно в **1.2 раза быстрее**. Это на **6 мс** меньше, то есть около **16%** времени. За одну секунду такой работы пул успевает сделать примерно на **19%** больше, чем вариант с постоянной отдачей процессора другим потокам.

Условия замера: буфер **256 КБ** (это ровно размер кэша L2 одного ядра на этой машине), **24 задачи**, в каждой **40 проходов** по своему буферу. Оба варианта посчитали одно и то же: контрольные суммы совпали.

`cargo test` проходит: **12 тестов** библиотеки и **1 doctest**.

## Слова, без которых дальше будет туман

**Процессор (CPU)** считает. Внутри него несколько независимых счётных блоков.

**Физическое ядро** — один такой блок. На i7-8750H их 6. У каждого ядра свои маленькие и очень быстрые хранилища: кэш L1 и кэш L2.

**Логический CPU** — то, что видит операционная система в списке процессоров. Их здесь 12, номера `0…11`. Это не 12 отдельных ядер. Intel называет технологию hyper-threading: одно физическое ядро притворяется двумя. Пара делит одни и те же L1 и L2.

На этой машине пары такие:

| Физическое ядро | Логические CPU | Общие кэши |
|---|---|---|
| 0 | 0 и 6 | L1 32 КБ, L2 256 КБ |
| 1 | 1 и 7 | L1 32 КБ, L2 256 КБ |
| 2 | 2 и 8 | L1 32 КБ, L2 256 КБ |
| 3 | 3 и 9 | L1 32 КБ, L2 256 КБ |
| 4 | 4 и 10 | L1 32 КБ, L2 256 КБ |
| 5 | 5 и 11 | L1 32 КБ, L2 256 КБ |

**L3** один на весь кристалл: 9 МБ, им пользуются все 12 логических CPU.

**Поток** — отдельная последовательность команд внутри одной программы. Потоки одной программы видят общую память. Операционная система решает, на каком логическом CPU поток работает прямо сейчас, и может пересадить его на другой.

**Пул потоков** — заранее запущенные рабочие потоки. Задачи не создают новый поток каждый раз, а встают в очередь к уже живому.

**Кэш** — маленькая память внутри процессора. Она в десятки раз быстрее оперативной памяти (RAM). Процессор сначала ищет данные в кэше. Если их там нет, он идёт в RAM. Это и есть дорогая часть.

Удобно думать о кэше как о столе, а об оперативной памяти как о шкафу в другой комнате:

- **L1** — то, что уже в руке. Мало места (здесь 32 КБ данных), зато мгновенно.
- **L2** — край стола. Больше (здесь 256 КБ на ядро), всё ещё очень быстро.
- **L3** — тумбочка рядом, общая на всех. 9 МБ.
- **RAM** — шкаф. Много места, ходить туда долго.

**Линия кэша** — порция, которой процессор обменивается с памятью. На этой машине линия 64 байта. Даже если нужна одна переменная, подтягивается вся линия.

**Working set** — те байты, к которым программа реально обращается в данный момент. Не вся память программы, а горячий кусок. В примере сравнения это буфер на 256 КБ у каждой задачи.

**TLB** — маленькая таблица, по которой процессор переводит адрес программы в адрес физической памяти. Смена *процесса* (другая программа, другое адресное пространство) эту таблицу сбрасывает. Потоки *одной* программы адресное пространство делят, поэтому между ними TLB целиком не выбрасывается.

## Что на самом деле происходит при переключении

Частая картина такая: «поток сняли с ядра — кэш стёрли и загрузили заново». Так процессор не делает. Линии L1, L2 и L3 остаются на месте.

Дорогое начинается, когда на это же ядро садится другой поток со своими данными:

1. Его байты не лежат в L1/L2 этого ядра.
2. Чтобы их прочитать, процессор тащит их из L3 или из RAM.
3. Новые линии занимают место. Старые, которые были нужны первому потоку, вытесняются.
4. Когда первый поток возвращается, его данные уже холодные, и плата за поход в память повторяется.

Отдельно дорого **переехать на другое физическое ядро**. L1 и L2 у нового ядра другие. Всё, что было горячим на старом, там отсутствует.

L3 при этом общий, поэтому часть данных может остаться в нём. Но L3 медленнее L1 и L2, и чужие данные его тоже вытесняют. Полной очистки L3 при переключении потока нет.

Из обычной программы нельзя запретить операционной системе вообще когда-либо снимать поток с ядра. Можно сделать так, чтобы это случалось реже и чтобы данные не метались между ядрами. Это и есть оптимизация `warm_core`.

## Что делает пул, шаг за шагом

При создании `Pool::new()` происходит следующее.

1. Читается `/sys/devices/system/cpu`: у каждого логического CPU берётся номер физического ядра, список соседей по hyper-threading и описание кэшей.
2. По умолчанию запускается **один рабочий поток на физическое ядро**, не на каждый логический CPU. На этой машине это 6 потоков, закреплённых за CPU `0, 1, 2, 3, 4, 5`. Второй номер пары (`6…11`) не занимаем: он делит с первым те же L1 и L2, и два наших потока на одном ядре выбивали бы данные друг друга.
3. Каждый рабочий поток привязан к своему CPU. Операционная система не переносит его на другое ядро. Маска разрешения содержит ровно один номер.
4. У каждого рабочего потока две очереди:
   - общая — для `execute`;
   - закреплённая — для `execute_on`.
5. Очередь — ограниченное кольцо на 4096 задач по схеме Вьюкова. Несколько потоков могут класть задачи одновременно, несколько могут забирать.
6. Индекс «куда положили» и индекс «откуда забрали» стоят на разных линиях по 64 байта. Слот задачи тоже выровнен на 64 байта. Иначе каждое добавление задачи портило бы ту самую линию, которую рабочий поток в этот момент читает. Ядра начинали бы гонять одну линию туда-сюда через L3. Это называется false sharing: данные логически разные, а физически лежат в одной линии.
7. Рабочий поток берёт до 32 своих задач подряд и считает их, не глядя в чужие очереди. Ядро остаётся на одном наборе данных.
8. Чужая очередь читается только когда своя пустая. Сначала смотрится самое загруженное ядро. Забираются только задачи из общей очереди.
9. Задачи из закреплённой очереди не крадутся. Их положили на конкретное ядро специально, чтобы данные остались в его L1/L2.
10. Если работы нет, поток засыпает (`park`). Новая задача его будит (`unpark`).

`Layout::LogicalCpus` меняет шаг 2: рабочий поток создаётся на каждый логический CPU, включая пару hyper-threading. Это имеет смысл, когда задачи почти не делят кэш. Для данных размером с L2 режим по умолчанию лучше.

## Как течёт одна задача

`execute` выбирает ядро с самой короткой очередью. Если длины равны, задачи раздаются по кругу, а не все падают на нулевое ядро. Задачу может забрать простаивающий сосед, если у него своя очередь пуста.

`execute_on(core, ...)` кладёт задачу именно на это физическое ядро. Сосед её не заберёт.

Оба вызова сразу возвращают `JobHandle`. Считать можно дальше, а результат забрать через `wait()`. `wait()` ждёт, пока рабочий поток выполнит задачу. Если задача паникует, паника всплывает в `wait()`, а сам рабочий поток остаётся жив и берёт следующие задачи.

Когда пул уничтожается (выходит из области видимости), он помечает остановку, будит всех и дожидается, пока уже поставленные задачи доедут до конца.

## Как этим пользоваться

```rust
use warm_core::{Config, CoreId, Layout, Pool, Topology};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Самый обычный пул: одно физическое ядро — один закреплённый поток,
    // пачка из 32 задач.
    let pool = Pool::new()?;

    println!("рабочих потоков: {}", pool.worker_count());
    println!("логические CPU: {:?}", pool.pinned_cpus());

    // Задача уходит на наименее загруженное ядро.
    // wait() блокируется, пока её не посчитают.
    let sum = pool.execute(|| 2 + 2).wait();
    assert_eq!(sum, 4);

    // Та же работа, но поток останется на ядре, которое мы выбрали.
    // Удобно, если следующие задачи трогают те же данные.
    let core = pool.cores()[0];
    let pinned = pool.execute_on(core, || 10)?.wait();
    assert_eq!(pinned, 10);

    // Явный режим. LogicalCpus сажает поток и на второй hyper-thread ядра.
    let _all_logical = Pool::with_config(Config {
        layout: Layout::LogicalCpus,
        batch: 32,
    })?;

    // Топология без пула: ядра, пары SMT, размеры кэшей.
    let topology = Topology::detect()?;
    println!("логических CPU в системе: {}", topology.cpus.len());
    println!("L2 одного ядра: {:?}", topology.l2_size_bytes());

    let _ = CoreId(0);
    Ok(())
}
```

`execute_on` возвращает ошибку `PoolError::UnknownCore`, если такого физического ядра в пуле нет.

Замыкание, которое передаётся в пул, должно быть `'static` и `Send`: его забирает другой поток, и оно не может держать ссылки на локальные переменные вызывающего. Нужные данные надо передать внутрь замыкания владением (`move`).

## Прирост на замеренной задаче

Замер — `examples/compare.rs`, сборка `--release`, машина Intel Core i7-8750H (6 ядер, 12 потоков, L2 = 256 КБ на ядро).

Оба варианта делают **одну и ту же** работу:

- 24 задачи;
- у каждой свой буфер на 256 КБ;
- 40 проходов: каждый байт буфера увеличивается на 1, по пути копится контрольная сумма;
- в конце суммы сравниваются, чтобы компилятор не выкинул цикл и чтобы оба варианта правда посчитали одно и то же.

Разница только в том, *как* эта работа сидит на процессоре.

**База.** 24 отдельных `std::thread`. Это вдвое больше, чем логических CPU, и вчетверо больше, чем физических ядер. После каждого прохода поток вызывает `yield_now()` и отдаёт ядро. На это ядро садится другая задача со своим буфером на 256 КБ. Буфер как раз равен всему L2, поэтому данные предыдущей задачи из L2 вытесняются. Когда она возвращается, проход начинается с холодного кэша. Плюс сама пересадка потока стоит времени.

**warm_core.** Те же 24 задачи, но их выполняют 6 заранее закреплённых потоков, по одному на физическое ядро. Между проходами никто процессор не отдаёт. Пока задача не закончила свои 40 проходов, её буфер остаётся рабочим набором этого ядра. Следующая задача этого же ядра начнётся только после пачки, а не после каждого прохода.

Результат прогона:

| | `std::thread` + `yield_now` | `warm_core` |
|---|---:|---:|
| Время | 37 мс | 31 мс |
| Во сколько раз | 1.0 | **1.2** |

Что эти цифры значат по-человечески:

- Сэкономлено **6 мс** на этой пачке работы: `37 − 31 = 6`.
- Пул потратил `31 / 37 ≈ 84%` времени базы. Остальные **16%** времени база отдала на переключения и на повторную загрузку вытесненных данных.
- «В 1.2 раза быстрее» — это `37 / 31 ≈ 1.19`, округлённо **1.2**. Та же работа заканчивается раньше, а не «делается другая, более лёгкая».
- Если такую пачку гонять непрерывно, за секунду база успевает около `1000 / 37 ≈ 27` пачек, пул — около `1000 / 31 ≈ 32`. Это примерно на **19%** больше выполненной работы за то же время.

Абсолютные 6 мс на одном коротком прогоне выглядят скромно. Прирост именно в доле времени, которую перестают тратить на холодный кэш и на отдачу ядра. Чем чаще одни и те же данные перечитываются и чем чаще потоки без пула прыгают между ядрами, тем заметнее эта доля. На задаче, которая и так один раз потоком читает память и больше к ней не возвращается, кэш почти не помогает: данные не успевают стать «горячими».

Повторить замер у себя:

```bash
cargo run --release --example compare
```

Пример печатает число логических CPU, число физических ядер в пуле, размер буфера, список закреплённых CPU и оба времени. Числа на другой машине или под нагрузкой будут другими. Отношение 1.2 — результат этого прогона на i7-8750H, не гарантия для любого процессора.

Посмотреть, из чего складывается разница, можно счётчиками ядра. Их собирает `perf`: промахи L1, промахи общего L3, переключения контекста и переезды потока между CPU.

```bash
perf stat -e L1-dcache-load-misses,LLC-load-misses,context-switches,cpu-migrations \
  cargo run --release --example compare
```

Ожидаемая картина: у базы больше `context-switches` и `cpu-migrations`, потому что потоки сами отдают CPU и система сажает их куда получится. У пула миграций почти нет: каждый рабочий поток привязан к одному номеру. `L1-dcache-load-misses` — сколько раз данных не оказалось в самом быстром кэше.

Тот же сценарий, но короче и через criterion:

```bash
cargo bench
```

Там 8 проходов вместо 40, размер буфера тоже 256 КБ. Criterion сам повторяет прогон и считает разброс. Это не замена примеру: пример проще читать глазами.

## Что проверяют тесты

`cargo test` запускает 12 тестов библиотеки и один пример из документации `src/lib.rs`.

Очередь:

- один поток кладёт и забирает значения, кольцо переполняется и корректно отказывает, когда оно полное;
- индексы постановки и снятия лежат на разных линиях по 64 байта;
- четыре потока кладут и четыре забирают 8000 чисел, ни одно не теряется и не дублируется.

Пул:

- 200 задач возвращают свои результаты;
- у каждого рабочего потока в маске ровно один CPU, и это тот CPU, за которым его закрепили;
- неизвестное ядро в `execute_on` даёт ошибку;
- паника внутри задачи не убивает рабочий поток: следующая задача выполняется;
- режим `LogicalCpus` поднимает рабочий поток на каждый логический CPU.

Топология и привязка:

- разбор списков CPU вида `0,6` и `0-3,8`;
- разбор размеров кэша `32K`, `256K`, `9M`;
- живая машина: кэш-линия — степень двойки, на одно физическое ядро приходится один рабочий поток;
- `sched_setaffinity` сужает маску потока до одного CPU.

Запуск:

```bash
cargo test
```
